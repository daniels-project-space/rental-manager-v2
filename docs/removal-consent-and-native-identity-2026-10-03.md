# Exact removal requests and Native offering identities

The legacy removal mutation verified the tool-selected booked line but did not establish that the current renter asked to remove it. A controlled unrelated camera-weight question could therefore remove a booked item. The existing Native baseline is `/root/rental-consent-boundaries-native-proof.json`; it is injected conflicting tool selection, not evidence of the actual model choosing that edit.

Removals now reconcile the latest real renter message with the Native booked offering, exact quantity and any stated booking period or reduction/remaining total. Questions, unrelated targets, wrong quantities/prices/periods, unanchored references and incomplete multi-line selections refuse without changing the order. “All” uses the actual booked quantity and “both” means exactly two units. Only a known priced Native offering can be removed. Existing lifecycle, named restrictions, current-message binding and idempotency checks remain.

Shared identity matching for BOTH addition paths and removals now derives identities from Native physical components and reviewed inventory aliases. A Sony FX3 advertising title mentioning A7S III cannot license an A7S III request. Bundle aliases retain their principal components; explicit camera-kit references identify the complete commercial kit. A main camera removal can identify its existing commercial kit, while a request to remove an included lens cannot delete the whole camera kit. Incomplete or unknown identities retain review. Native Remus aliases preserve the actual focal length.

A committed removal stores its Native product/quantity/identity/aliases in the append-only change ledger. Retrying after the line has entirely disappeared can resolve the original offering and return the current order with action_performed:false, rather than deleting more units or claiming a new action.
