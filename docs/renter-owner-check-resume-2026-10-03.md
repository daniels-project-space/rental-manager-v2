# Resume owner checks from Native workflow state

The fresh production reply asked whether to check a lens after the renter already requested that check. Native had saved the owner task, but get_renter_context did not include the owner-check ledger. The first tool result described a proposed check without indicating that customer permission was not required. A second request message could also create another pending task because retry identity included the message ID.

The bot now receives bounded Native task history through get_renter_context and the canonical preloaded context. The actual agent tool output schema preserves the task fields, including pending/handled status, requirements, candidates and whether the booking context changed. Handling notes are excluded, and specification_result_verified=false makes task handling distinct from verified equipment data. The first search exposes owner_review_workflow and the transactional persistence step. The shared prompt describes continuation of the already requested work, rather than repeated customer permission or internal-system explanations. This is workflow grounding, not a phrase-replacement filter.

Native persistence reuses a pending task only for the same thread/account, current booking context, normalized mount, requirements, dates and quantity. It refreshes the candidates using the newly revalidated Native result while retaining the original source question. It does not reopen handled tasks; a renewed request can create a new pending task. A changed booking context does not reuse the old pending task. Existing stale-save gates and inventory/specification validation remain in force.

An owned Native lab fixture checked new task creation, repeated-request deduplication, original source retention, continuation after an owner reply, handled status without specification attestation or handling-note exposure, a renewed request, and changed-context separation after one explicitly requested lab date extension.
