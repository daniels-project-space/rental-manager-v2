# Atomic Lab replacement acceptance

A replacement needs one booking transaction. Separate removal and addition can leave an agreed rental missing its original item when the replacement fails. `modify_booking` now exposes `replace_items`, backed by `applyReplacementBasket` and the same Native `prepareEquipmentProposal` used to quote the complete basket.

The current inbound message and server thread own the request. Native checks the exact removed listing/quantity, retained gear, complete compatible selected group, actual account prices and dated shared-stock allocation before a single order patch. An exact directional instruction must agree to the full Native price, or the current reply must accept one quote actually recorded in the immediately preceding owner message. Quote-only, ambiguous, stale, conditional, conflicting and changed requests leave the basket intact. Collected or closed rentals remain held for owner review. Real rental writes and real chats remain gated.

Replacement evidence carries exact commercial selections, base/removed/added members, both the original and proposed physical identity keys, dates and full prices. Native quote capture checks current draft approval and basket context before preserving this metadata on an owner message. It is quote evidence, not consent. Acceptance independently re-resolves the original and proposed equipment and checks the stored offer against the current context, epoch, price and physical mappings. Addition consent cannot consume replacement records. A server-bound message/selection key makes successful retries return the current basket with `action_performed:false`; only the first accepted transaction records a revision and context transition. Legacy single-item and group addition/removal paths refuse splitting the same inbound swap.

The deployed acceptance check exposed a shared reference gap: zoom shorthand was recognized, while “TTArtisan 11mm” could not identify the complete Native prime-lens name. The shared lens-reference builder now handles primes as well as zooms, retaining unique identity and explicit brand/mount disambiguation. Both price and stock callers use this shared resolution. Unknown or competing prime identities are refused.

The Mastra booking-read tool also used the marketplace order API even in Lab conversations. It now reads the current Native Lab order through the server scope; a model-supplied foreign order/account cannot redirect the read, and no marketplace action is called. Real booking reads through this tool remain gated pending rollout authorization.

Validation: 407 unique focused transaction, consent, price, receipt, stock and tool-scope checks; project/backend typechecks. The deployed actual Mastra SDK flow quotes an owned Lab booking, rejects a quote-only edit and invalid removal, records the previously captured actual model offer, accepts “Yes please”, commits the £42-to-£40 swap once, rejects a separate removal, blocks writes in diagnostic scope, returns an unchanged basket on retry and reads that exact current state through the booking tool. Nine Native calls verify the final SDK flow. Fixtures are cleaned. No new model generation, marketplace request, real rental write or real message was needed. Proof: `/root/rental-atomic-replacement-native-proof.json`.

The first check stopped on a missing test-only run ID; a corrected check then exposed the prime-reference failure and held acceptance without changing the order. Both failures were cleaned, and the final check passed after the shared resolver fix. This is controlled Native execution using a previously captured model offer, not a fresh model choosing the new tool.

Open: fresh multi-turn model behavior with the new action is not yet proven. Compatibility planning still reuses the addition planner and can conservatively hold replacements that change camera mounts. General owner pricing tasks, catalogue discrepancies, phone push longevity and the complete original production-readiness requirements remain unfinished. No real Hygglo activation or migration is authorized.
